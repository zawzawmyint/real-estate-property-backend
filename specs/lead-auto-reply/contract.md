# Website enquiry email contract

Status: Implemented locally — 2026-11-20. Backend authority for P2-01; copy verbatim to frontend `docs/contracts/lead-auto-reply.md`. Production activation remains separately gated.

## Existing public HTTP contracts

- `POST /api/v1/public/properties/:propertyId/inquiries`: existing `{submissionId,name,phone?,email?,message?}` body and property eligibility rules remain unchanged.
- `POST /api/v1/public/inquiries`: existing general enquiry body and validation remain unchanged.
- New acceptance: 201 `{received:true}`. Matching receipt replay: 200 `{received:true}`. Existing validation, relay, rate-limit, unavailable-property and conflict errors remain unchanged. No email status, recipient, queue ID or lead ID is returned.
- At least one contact method remains required. Persist email work only for a new accepted submission with an email while `EMAIL_ENQUIRY_NOTIFICATIONS_ENABLED=true`. Disabled mode creates no work and has no retrospective catch-up.

## Internal producer and payload

The acknowledgement producer accepts `{leadId:string,to:string,name:string,property:null|{id:string,title:string}}` inside the same transaction as enquiry creation and persists a UUID notification ID with `dedupeKey=WEBSITE_ENQUIRY_RECEIVED:<leadId>`. This internal identifier contains no personal data and needs no HMAC or deduplication secret. The shared outbox now supports other typed kinds; this contract remains the P2-01 acknowledgement compatibility record. See [shared transactional email notifications](../../specs/transactional-emails/spec.md).

Payload v1 is `{to:string,name:string,publicOrigin:string,brand:string,replyTo:string,property:null|{title:string,url:string}}`. The optional public URL is built from validated `APP_ORIGIN` and encoded property ID, never user-supplied links. Payload validation occurs at write and consumption boundaries. The kind is `WEBSITE_ENQUIRY_RECEIVED`, template version is `1`, and queue is `transactional-emails`. The exact validated public origin, brand/display name and reply-to are immutable snapshot fields. At consumption, property URLs are validated against that snapshot origin, not a later worker `APP_ORIGIN`. The message uses snapshot display name/Reply-To and the current configured SMTP sender address; SMTP credentials and sender address are never payload-controlled.

## Authoritative ledger

Shared delivery adds nullable recipient user, viewing, task, event-version and schedule context fields as defined in [shared transactional emails](../../specs/transactional-emails/spec.md). They do not change the acknowledgement payload or dedupe key below.

Prisma model `EmailNotification` has `id`, unique `dedupeKey`, `kind`, `templateVersion`, nullable `leadId` (foreign key with `onDelete: Restrict` when present), nullable unique `replayOfId`, `status`, encrypted payload ciphertext/IV/tag/key ID, `createdAt`, `nextAttemptAt`, nullable `expiresAt`, `enqueuedAt`, `submittedAt`, `terminalAt`, `leaseToken`, `leaseUntil`, `dispatchAttempts`, `sendAttempts`, `lastErrorCode`, and nullable `providerMessageId`. It indexes due status/time and terminal retention scans. The enquiry producer requires a lead ID; the shared delivery repository does not require one for every future kind. This ledger is independent of the staff notification inbox.

States: `PENDING`, `ENQUEUED`, `SENDING`, `SUBMITTED`, `FAILED`, `UNCERTAIN`, `EXPIRED`, `SUPPRESSED`. Terminal states never send automatically. `SUPPRESSED` is used by shared non-enquiry kinds when current context invalidates pending work; this acknowledgement kind retains its existing immutable eligibility. `SUBMITTED` records SMTP acceptance only. Expiry is 24 hours after enquiry creation; do not start new SMTP attempts once expired. Do not expire an active `SENDING` row as proof that nothing was sent.

Encrypt payload with AES-256-GCM, random 12-byte IV, 16-byte tag and AAD binding notification ID, kind and template version. Keep key IDs for rotation; retain old keys until dependent payloads are purged. Missing keys pause/defer work and fail worker readiness without spending SMTP attempts; malformed/authentication-failed payloads become `FAILED`. Logs expose IDs, status and allowlisted error codes only.

## Queue, worker and retry policy

- Job name `send-email`; data exactly `{notificationId:string}`; job ID is the UUID without a colon. BullMQ `attempts:1`; retain completed jobs for 24 hours/10,000 records and failed jobs for seven days/10,000 records. Ledger claims remain authoritative after Redis retention/removal.
- Dispatch every second, at most 50 due rows per tick, ordered by `nextAttemptAt`, `createdAt`, then ID. Dispatch selection always excludes expired rows and rows with missing payload keys; reconcile unfinished enqueued work every 30 seconds. Prevent overlapping ticks. Recreate missing jobs, remove terminal Redis jobs only when the ledger still requires processing, and never delete active jobs. Dispatch leases last 30 seconds. Token-conditional transitions cannot overwrite a row already claimed for sending or a terminal outcome.
- Atomically claim due `PENDING`/`ENQUEUED` rows as `SENDING`, increment sendAttempts, and grant a 60-second lease. SMTP concurrency defaults to 2. Fence completion by status and token; stale workers cannot commit results.
- Maximum four SMTP attempts. After retryable failures 1/2/3, schedule delays of 60/300/1800 seconds, capped by expiry. Exhaustion is `FAILED`. Redis publish failures retry after five seconds without consuming SMTP attempts.
- Retry only explicit temporary SMTP rejection or a provable connection/pre-DATA failure. Authentication/envelope/permanent SMTP rejection is `FAILED`. Ambiguous failure during/after DATA, expired send lease, or SMTP success followed by failure to durably record success is `UNCERTAIN`; never automatically resend. Guarantee durable intent and guarded retries, not exactly-once email delivery.
- An already-enqueued job with an unavailable payload key completes its Redis execution without spending an SMTP attempt or repeatedly moving to delayed. Keep its unfinished ledger row; readiness stays unavailable. Once the key is restored and the worker restarted, dispatcher reconciliation recreates the job from the ledger. Blocked-key jobs may use one queue activation but must not loop and monopolize the send rate budget.
- For ledger-scheduled retries, use BullMQ `moveToDelayed(nextAttemptAt, token)` and `DelayedError` so the existing job remains scheduled. Do not combine independent BullMQ retries with ledger retries.
- SMTP connection/greeting timeouts: 10 seconds each; socket timeout: 15 seconds; target a 30-second total send deadline. Before worker implementation, pin the SMTP transport and prove its supported in-flight cancellation behavior with a stalled SMTP server. A bare Promise timeout or ordinary transporter `close()` is not proof of cancellation. The sender must own each active attempt so aborting one cannot silently abort another. On deadline, mark acceptance-ambiguous work `UNCERTAIN`, observe/terminate its underlying send, ignore late completion for ledger transitions, and never retry while it can still execute. If the pinned library cannot safely abort an active send, revise this sender boundary before implementing it rather than promising an unsupported deadline. Graceful shutdown stops dispatch/intake and drains for at most 35 seconds; the verified abort path then closes unfinished sends and workers/Redis/Prisma with bounded cleanup.
- Run one non-overlapping maintenance pass at startup and before each one-second dispatch tick. In indexed, token-conditional batches of at most 100 rows per category: recover expired `SENDING` leases as `UNCERTAIN`, mark expired `PENDING`/`ENQUEUED` rows `EXPIRED`, purge terminal payloads older than seven days, and remove terminal metadata older than 90 days. Never expire an active send as proof of non-delivery. Bound each pass; unfinished housekeeping continues next tick. Excluding ineligible rows in the due query prevents an expired/key-blocked backlog larger than the batch size from starving eligible sends. Log maintenance errors safely and fail readiness until database maintenance/dispatch progress resumes.
- `/health` and `/ready` bind to loopback on worker port 4312 by default. Readiness requires database access, needed payload keys, connected Redis, running/unpaused consumer and a successful dispatch tick within 30 seconds; this is not proof of provider availability or inbox delivery. Redis-down readiness is 503 while the public API can still capture enquiries.
- Redis uses AOF persistence and `maxmemory-policy=noeviction`; use authenticated verified TLS in production, environment-specific prefixes and dedicated connections. Do not reuse BullMQ connections for future notification Pub/Sub. Never flush shared Redis.

## Configuration and operations

Backend-only keys include `EMAIL_ENQUIRY_NOTIFICATIONS_ENABLED=false`, `EMAIL_STAFF_NOTIFICATIONS_ENABLED=false`, `EMAIL_CUSTOMER_VIEWING_NOTIFICATIONS_ENABLED=false`, `EMAIL_CUSTOMER_VIEWING_ACTIVATED_AT` (required UTC cutoff when customer viewing mail is enabled), `REDIS_URL`, `EMAIL_QUEUE_PREFIX`, `EMAIL_CONCURRENCY=2`, `EMAIL_RATE_LIMIT_MAX` (required positive queue-wide send count per window), `EMAIL_RATE_LIMIT_DURATION_MS=1000`, `EMAIL_WORKER_HEALTH_PORT=4312`, `EMAIL_PAYLOAD_KEYS` (JSON key ID to 32-byte base64 key), `EMAIL_PAYLOAD_ACTIVE_KEY_ID`, `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE`, `SMTP_USERNAME`, `SMTP_PASSWORD`, `SMTP_FROM`, `SMTP_REPLY_TO`, and `EMAIL_BRAND_NAME=Avenor`. Secrets are validated without logging values. The API producer needs payload encryption/brand configuration only when any group is enabled; it does not need Redis or SMTP connectivity. The worker requires keys, Redis and SMTP even with production groups disabled so it can drain.

SMTP uses 465 with implicit TLS or 587 with mandatory STARTTLS; require credentials and a verified sender in production. Reference credentials may be reused locally as authorized; queue prefix, encryption keys and branding belong to this application. Sender/reply-to and provider quota remain activation gates. Configure provider rate limiting after verifying the actual account limit, before live activation. Enforce the configured queue-wide send rate across workers, not just per-process concurrency. A separate queue/application, including book-store, has its own limiter even when sharing SMTP credentials. Before activation, document the total account allowance, reserve a conservative real-estate share of the per-window and daily quota with headroom for other senders, and define the owner/alert for quota exhaustion. Provider-enforced quota rejection is classified by its actual SMTP response and never bypassed by retry or replay. Use separate provider credentials/subaccounts if budgets cannot be allocated reliably; do not build a cross-project quota service for P2-01.

Commands are `email:worker` (Node + tsx), `email:worker:start` (compiled Node), `email:inspect -- --id <uuid>`, and `email:replay -- --id <uuid>` (read-only preview), with `--apply --acknowledge-duplicate-risk` to replay. The compiled operator is `src/modules/email/email.operator.ts`; there is no `scripts/email-operator.ts`. CLI access is trusted operator access; no public/staff HTTP management route exists. Inspect returns redacted metadata only. Replay creates at most one child for each original attempt under the unique non-null `replayOfId` constraint and `dedupeKey=replay:<originalId>`. Apply requires both flags and returns an existing child rather than enqueueing another, including after lost output or concurrent execution. A new child requires a retained, unexpired `FAILED`/`UNCERTAIN` original and does not change its recipient. Each child retains the original expiry. The receipt remains authoritative; receipt replay never recreates deleted ledger rows.

## Delivery evidence and activation limits

Nodemailer 10.6.0 AbortSignal cancellation, BullMQ 6.7.8 and ioredis 6.0.0 are the pinned implementation. Nodemailer’s bundled declarations are used; the redundant `@types/nodemailer` package was removed. Isolated tests used Redis 7.2.4; local compose and CI pin the Redis 8.2.10 image, which was not executed by this delivery. No live SMTP email, normal-database migration, deployment, reference-Redis availability, authorized sender/reply-to validation, provider quota validation or inbox-delivery observation is claimed. Before enabling production, set the flag only after completing the operational gates above.
